## 1 目标与现状

次数筛选已支持全部、仅1次和至少2次，但任务视图只显示“匹配任务 X/Y”。一个匹配组可能包含多条请求，只看组数不能判断筛选覆盖多少窗口请求。

下一批在现有匹配说明中增加请求覆盖计数，显示匹配组包含的完整窗口请求数与当前窗口总请求数。复用[overview.js](../../internal/localadmin/assets/overview.js)的modelTaskUsageText(value,groups)、g.count及value.count，不新增筛选器、后端数据、网络请求或导出字段。

历史预算900000、[其他待验收和暂缓项](remaining-acceptance.md)保持，不为累计5项拆分开发步骤或自动启动未授权目标。

## 2 展示与统计契约

入口保持登录后台 → 运行概览 → 模型接口请求 → AI费用风险提示 → 按任务查看用量。无需额外权限，未来实现并部署后刷新后台生效。本轮不提前修改已实现功能的使用步骤。

将现有匹配行扩展为：

> 匹配任务 2/3；匹配任务内窗口请求 5/6次；展开任务查看全部窗口内请求。

X/Y分别为匹配组数和窗口全部组数；N/M分别为匹配组g.count之和及value.count。文案明确“匹配任务内”，避免误解为逐请求匹配数量。分母不随筛选变化；不显示百分比、不推算费用、不添加风险程度或颜色等级。

### 计数范围

- 先按现有风险、结果、次数条件选出任务组，再合计这些完整组的g.count。风险和结果可由不同请求命中，未命中条件的组内请求也计入覆盖数。
- 单次请求同时命中多个风险提示只计一次；不要把风险提示计数相加，也不要按结果数量拼出请求总数。
- 无筛选时N=M，组数X=Y；非空窗口无匹配时显示0/Y和0/M，并保留“当前条件无匹配任务”。零覆盖不表示零费用。
- 排序只改变展示顺序，不改变两组计数；返回原顺序、改变展开状态均不改变覆盖数。
- 独立请求继续逐条成组，重复id不去重。跨会话同任务仍按现有规则隔离；Token字段缺失不影响请求计数。
- 只统计最近最多256条已结束请求。窗口截断、刷新后新请求或淘汰请求改变分组时，以本次快照重算；不补查历史，不跨启动累加。
- value为空或统计窗口无效时沿用原有未知提示；有效空窗口沿用“暂无近期请求，任务用量未知”，不新增0/0行。

示例夹具：A组1次，B组2次，C组3次。选择至少2次时显示2/3组、5/6次；风险与结果交集只保留B时显示1/3组、2/6次，即使B内只有一条请求命中风险也仍为2次。

## 3 与现有操作的关系

改变筛选或应用费用阈值后，与匹配任务一起重算覆盖数。未应用的阈值草稿不改变结果。重置任务视图恢复全部条件和原顺序，覆盖数回到M/M，保留已应用阈值及草稿。

手动/自动刷新按新快照更新分母和分子；读取失败清除旧内容并保持既有禁用策略，恢复后再计算。跨启动、离页、退出和认证失效按原生命周期处理，不遗留前一窗口数字。

继续保留同键可见任务展开与焦点，不增加自动聚焦或滚动。摘要五段、逐请求正文、费用提示与全部JSON报告不变；报告仍包含完整快照，不能把新文案当成新增报告字段。该计数不证明任务完成、QQ收件或完整账单。
