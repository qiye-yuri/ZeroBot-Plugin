# 官方开发进展监控

`updatewatch` 是独立插件，当前适配 FTB Evolution 2。由机器人进程定时检查，不依赖 ChatGPT 定时任务。公开来源出现内容变化后才调用已有模型判断重要性、合并事件并生成中文私聊；没有实质进展不发送通知。RSSHub及独立GitHub搜索插件已删除；本功能的官方来源抓取、核验与去重独立保留。

## 使用与配置

登录本机后台后，点击左侧 **更新监控**，直接调整启用开关、1～168 小时检查间隔、模型入口、私聊主人、发送机器人、官方来源开关、关联仓库及公告链接，再点击“保存监控设置”。无需编辑 JSON 或重启。页面显示最近检查、基线来源数、待发数及来源错误。

模型下拉框显示入口及其当前模型名；模型名称、接口与密钥在 **AI 设置** 中管理。接收人只能选择已配置主人；如需增加主人，先到连接设置按其流程配置。机器人可选择在线账号或填写自己的离线账号。

保存前自动备份旧配置到 `.local/updatewatch/backups/`；并发修改会要求重新加载，错误时保留草稿。切换后台页面保留未保存内容；“重新加载 / 放弃草稿”丢弃草稿。检查期间读写会提示稍后重试，防止与抓取或投递冲突。保存不主动触发检查，下一次调度按最新间隔判断是否到期。

仅机器人主人可在私聊中使用以下命令；不提供群通知。配置文件不存在时默认关闭。

| 命令 | 作用 |
| --- | --- |
| `更新监控开启` | 开启，并在接收人/机器人未指定时绑定当前主人和机器人 |
| `更新监控暂停` | 暂停自动检查及待发消息投递，保留基线 |
| `更新监控状态` | 查看开关、间隔、最近检查、待发数、来源失败和错误 |
| `更新监控测试通知` | 向已配置主人发送标注为测试的私聊，不访问来源/模型，不修改计划、基线或待发队列；仅主人私聊可用 |
| `更新监控配置` | 查看无密钥的当前配置 |
| `更新监控间隔 24` | 每24小时检查，支持1～168小时 |
| `更新监控模型 Summary` | 使用现有总结入口；也支持Chat、GPT、Agent |
| `更新监控检查` | 手动检查，即使监控暂停也执行；有重要新内容会发送通知 |

检查中的命令会提示稍后重试。配置修改最迟一分钟生效，不需要重启机器人。间隔从最近完成检查计时，不是固定钟点；关机期间不执行，恢复后补查一次，不重放每天的检查。

完整配置位于项目根目录 `.local/updatewatch/config.json`：

```json
{
  "enabled": true,
  "intervalHours": 24,
  "ownerId": 0,
  "botId": 0,
  "modelRole": "Summary",
  "curseForge": true,
  "ftb": true,
  "github": true,
  "repositories": ["FTBTeam/FTB-Evo-Companion"],
  "announcements": []
}
```

接收人0表示采用唯一的已配置主人；多个主人时必须填其中一个账号。机器人0表示采用唯一在线机器人；多个在线账号时必须明确指定。可在后台更换账号并保留基线与历史去重；若旧对象仍有待发消息，必须先完成投递才能切换，防止旧消息转发给新对象。

上述配置均可在后台“更新监控”页面修改；开关、间隔和模型也可通过私聊修改。后台插件列表可管理 `updatewatch` 启停，个人范围停用也会阻止自动通知。模型接口、密钥及命名模型选择仍在现有AI后台配置，不复制密钥；模型入口选择与其他对话互不修改。实际模型请求会计入GPT类别统计，可能产生原服务商用量。

## 官方来源与核验范围

- 优先请求 CurseForge 的文件列表及文件更新日志。HTTP 403或页面结构不匹配记为来源失败，不绕过访问限制、不采用搜索摘要推断版本。
- FTB官网使用其公开版本接口与对应版本ID的完整更新日志，核对显式版本标题。保留官网和原始日志链接；查看最近20个版本。
- GitHub匿名读取 `FTB-Modpack-Issues` 的 `FTB Evolution 2` 标签最近更新的100条issue，仅将维护者控制的 `state: Fixed in Dev` 状态及OWNER/MEMBER回复作为确定进展证据；普通玩家标题只作为识别上下文，不将玩家报告认定为已证实问题或已修复。无法核实修复日期时明确标记“日期未核实”。未更新issue的回复使用本地缓存，避免反复消耗匿名额度。
- 配置仓库只允许FTBTeam官方组织：读取最近30个release和默认分支最近50个commit。默认仅FTB-Evo-Companion；增加仓库前应核实与整合包的官方关联。提交属于开发中，组件release不等于整合包已收录。
- 不读取登录态GitHub/Discord，不把Discord邀请页当公告。`announcements` 可配置FTB官网公开转载的具体文章URL；要求正文存在article及可识别的发布日期，否则记录无法核实。当前没有可核验的Discord公告输入，不宣称已查阅Discord。

数量上限之外的历史、非默认分支、未发布PR和未公开消息不在本轮抓取覆盖中。抓取失败的来源会在状态中单独列出，其他成功来源继续运行；第一次恢复或新增来源建立静默基线。检查失败不会清空旧记录。

同版本跨来源日期或版本冲突时不发布该事件。FTB日期由官方发布时间戳转换为UTC日期；不能从最后更新时间猜测发布日期。来源之间的内容变化交给模型结合旧正文、已发历史和待发队列核验；输出必须包含匹配原文的证据。格式/证据不合格时最多即时纠正一次，仍失败则保留待处理变化并报错。模型仍可能判断失误，证据校验不等于人工事实核验；通知附带原始来源便于复查。

## 去重、离线与维护

首次运行静默建立基线，不重发已知1.4.0等历史消息。以版本、发布ID、提交SHA、issue编号和正文保存记录；跨来源事件合并，语义重复由模型对比已发历史排除，仅有重要新增事实才补充。

`.local/updatewatch/state.json` 保存基线、待发队列、历史通知、来源错误和检查时间；`source-cache/` 保存公开issue缓存。发送前先持久化待发内容；离线或发送失败保留待发内容，在线后每分钟尝试投递。状态损坏时停止处理，不默默重置。模型失败不消耗事件，自动重试间隔至少30分钟；全部来源失败则留错误，按正常间隔再查。

QQ发送成功但回执丢失、或进程恰在发送成功到保存回执之间中断，可能重复发送；无法保证跨网络的严格一次投递。备份、恢复时需暂停/停止机器人并整体保留本目录。删除状态会重新建立基线；不要通过删除状态解决未知错误。

本机必须开机联网、ZeroBot进程运行。OneBot离线不影响来源检查，但消息要等机器人上线。原ChatGPT追踪任务不会自动删除或暂停，避免丢失原记录；如不再需要其通知，应在原任务页面自行暂停。

## 构建与验证

```powershell
go test ./internal/updatewatch ./plugin/updatewatch -count=1
go run ./cmd/updatewatch-check
go generate main.go
go build -trimpath -o .local/bin/zerobot-updatewatch.exe .
```

只读来源检查命令不调用模型、不发QQ消息；可追加一个本地输出路径保存公开证据。程序部署按[运行维护](operations.md#已验收程序部署与回退)操作，保留原配置、电量提醒及OneBot登录。

自动化覆盖：首次静默基线、源恢复基线、变化/重启去重、离线待发、模型失败重试、证据和输出格式校验、日期冲突、来源白名单、模型入口复用。真实来源与部署结果见[本次验证](updatewatch-verification.md)。

## 正式版本检查时机与分段结果

自动检查间隔从最近成功检查完成时起计算。若版本在一轮检查之后发布，24 小时间隔下可能接近一天后才发现；可在后台“更新监控”缩短间隔，或主人私聊发送“更新监控检查”立即检查。没有抓到版本与模型认为无需通知是不同情况。

模型有时将同一版本的新增功能和关键修复拆成多条结果。现在会先逐条校验证据，再把事件编号重叠的结果合并为一条通知；不会因同一版本编号重复而整体拒绝，也不会绕过原文证据检查。已有基线、待发与已发记录保留。

## 每日固定时间

后台“更新监控”新增“每日固定时间（北京时间）”，例如 `09:00`。填写后按每日固定时间运行，小时间隔暂不使用；清空后恢复间隔模式。修改时间从下一个时点开始，不因保存立即补发。时区固定为北京时间，不随电脑时区变化。调度器每分钟检查一次，实际通知在抓取和模型核验完成后发送；无实质变化不通知。

当天到点未开机、之后开机可补查一次；不重放错过多天的任务。离线待发通知仍在机器人上线后补发。私聊“更新监控检查”仍可立即检查；“更新监控间隔 N”会退出每日模式并改回小时周期。

通知使用标准消息列表发送。只有QQ返回成功状态、零错误码及非零消息编号，才移出待发队列；失败或回执不明保留待发项，后续投递仍可能重试。测试通知不代表真实开发进展，实际来源更新到通知的完整链路仍需单独验收。

多条待发通知按顺序投递，中途失败即保留该条及后续项，下次从未确认成功的项续发。已保存成功回执的项重启后不会重发；若QQ已成功接收、但程序在保存回执前异常退出，仍可能重复发送，当前不保证严格仅送达一次。全部来源暂时失败不会清空既有基线和待发队列。上述恢复分支已通过合成回执与临时状态文件验证，实际官方更新通知仍单独验收。
