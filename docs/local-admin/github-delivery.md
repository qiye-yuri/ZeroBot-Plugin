## 文件范围

| 文件类别 | 处理 |
| --- | --- |
| 产品源码、必要依赖与构建/测试配置 | 上传；本地替换的依赖实现须随源码完整提供 |
| README、使用步骤、配置示例、运行维护 | 上传，配置示例不含真实凭据 |
| 需求、设计、开发和必要测试说明 | 上传可复用内容及验证摘要，标明真实/隔离范围 |
| 对话逐字记录、会话总结、临时问答草稿 | 保留本机，不上传 |
| 本机调试截图、私有验收证据、日志、聊天档案、运行库及配置备份 | 保留本机，不上传 |
| 非使用/开发用途的对话衍生文档 | 不上传；不能仅因位于docs目录就认为可公开 |

`.local/`与插件内生成的运行数据已忽略；`docs/local-notes/`用于本机对话资料，也已忽略。忽略规则不会自动保护已跟踪文件，最终以拟提交清单及差异检查为准。不要删除本机资料，不要将已有数据子模块的运行变化作为源码更新一并提交。

按内容用途筛选已有文档，日期化名称不是排除依据。将公开使用/开发说明中的真实账号、群号和本机路径改为示例；私人原始证据保留本机，公开文档只保留必要验证摘要。修正公开索引对不上传资料的链接，避免读者打开失效文件或被要求访问开发者的私有目录。

## 中文格式和交付步骤

1. 汇总第一版行为、配置迁移/生效方式、验收结果和限制，检查使用与开发文档是否同步。
2. 按上述范围列出拟提交文件，核对差异、引用、生成文件、私有内容与依赖完整性；只暂存清单中的文件。
3. 完成适合最终变更的检查，使用中文提交说明。类型使用`feat`、`fix`、`docs`、`test`、`chore`等，如`feat: 增加本地机器人管理后台`；正文说明必要影响和验证。
4. 将提交推送到用户仓库。PR采用中文标题，按仓库模板写清“变更说明、验证结果、使用与兼容性、限制与待办”，不能写“全部通过”掩盖未验收范围。
5. 如本次版本计划包含正式版本发布，核对版本和标签后整理中文版本说明，按“新增、修复、变更、升级说明、验证与限制”组织；只上传计划中的公开交付产物。
6. 记录实际提交、分支、PR或版本链接及结果。未成功完成的环节保持待办，不能只准备了说明就记作已发布。

权限及文件边界同样适用于后续版本。本说明不要求重复申请用户已授权的正常仓库更新，但发布必须满足“第一版完成后”的条件。

公开交付文件按清单检查；中间交流、本机调查与原始开发记录统一放在docs/local-notes并整体忽略。该目录的资料不会因位于docs中而被提交。
